## 2. Creating the Backend Project and Using uv

### 2.1 Why This Project Uses uv

Official website: https://docs.astral.sh/uv/

First, let's understand it in one sentence: `uv` is a modern tool for managing Python projects, virtual environments, and dependencies.

This chapter needs to establish an understanding first: this project aims to adopt an engineering approach that is closer to **real enterprise development**, rather than just making the code "able to run."

In the Python ecosystem, the approaches people were previously familiar with generally fall into two categories:

- Using `venv + pip` in combination, where `venv` is responsible for creating virtual environments and `pip` is responsible for installing dependencies.
- Using `conda` directly, which uniformly manages the environment and dependencies.

In this project, however, the choice is `uv`. Compared with traditional approaches, it is more like an **all-in-one solution**: it unifies actions such as creating projects, creating virtual environments, installing dependencies, removing dependencies, and synchronizing environments into the same set of commands.

Its main advantages are:

- **Faster speed**: `uv` is written in `Rust`, and environment creation and dependency installation are usually faster than traditional approaches.
- **More convenient engineering**: project initialization, dependency management, and virtual environment management are unified in one set of commands.
- **Better team collaboration**: dependencies are written into `pyproject.toml` and lock files, making it easy for others to quickly synchronize the environment after pulling the project.

In one sentence: **In "Shopkeeper Data Q&A," `uv` is responsible for managing both the virtual environment and project dependencies, and is the foundational tool for the backend development environment.**

> **Supplementary understanding: What is the relationship between `uv` and `venv`?**
>
> You may ask: since we are using `uv`, why do we still see `.venv` in the project directory?
> The reason is not complicated: at the virtual environment level, `uv` essentially still works around Python's `venv` mechanism.
> That is to say:
>
> - `venv` is responsible for the "virtual environment" aspect.
> - `uv` is responsible for integrating the processes of "creating environments, initializing projects, installing dependencies, and locking versions."
>   Therefore, it is normal for `.venv` to appear in the project directory; this does not mean that `uv` is not being used.

### 2.2 Installing uv

Before using `uv`, you need to install it in the system environment first.

The most direct way is to use `pip`:

```bash
pip install uv
```

If the download speed is slow, you can also use a domestic mirror:

```bash
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple uv
```

If you are using macOS, run:

```bash
brew install uv
```

**Note:**

- This step does not require activating an existing virtual environment first.
- What is installed here is the system-level `uv` tool.
- Later, when creating a specific project, `uv` will generate an independent `.venv` for that project.

After installation is complete, you can check first:

```bash
uv --version
```

If the version number is output normally, it means `uv` is ready to use.


### 2.4 Common uv Commands

In this project, the most commonly used `uv` commands fall into three categories:

- Add dependencies: `uv add`
- Remove dependencies: `uv remove`
- Synchronize dependencies: `uv sync`

**Adding dependencies**

If you want to add a new dependency to the current project, you can use:

```bash
uv add 包名
# 例如
uv add fastapi
```

After execution, the dependency will be written to `pyproject.toml`.

**Removing dependencies**

If you want to remove a certain dependency, you can use:

```bash
uv remove 包名
# 例如
uv remove fastapi
```

**Synchronizing dependencies**

`uv sync` is a very important command in this project. Its role can be simply understood as:

> Based on the current project's `pyproject.toml` and `uv.lock`, synchronize your local environment to the correct state.

For example, when you receive project code from someone else, the most common approach is not to install dependencies one by one yourself, but to directly run:

```bash
uv sync
```

This way, it will read the dependencies already declared in the project and automatically complete the environment.

## 3. Create the Basic Services Required by the Backend

In addition to the frontend and backend code environments, this project also depends on several types of basic services. Let us first build an overall understanding here; the next chapter will continue to expand on the specific configuration of these basic services.

### 3.1 Basic Services Overview

This project mainly uses the following services:

| Service                       | Main Purpose                                                                                                                                                                                             |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MySQL`                    | Stores metadata information for the data warehouse, including table information, field information, and metric information; it also serves as the business data warehouse to simulate a real data warehouse scenario                                                                                       |
| `Qdrant`                   | Serves as the vector database, storing vector representations of field information and metric information; when users ask questions, the system retrieves the most relevant metadata through semantic similarity, providing highly relevant context for SQL generation                                                        |
| `Elasticsearch`            | Builds inverted indexes for actual values of dimensional fields; when natural language descriptions such as "North China region" and "digital category" appear in user questions, full-text search can match actual field values in the database, providing the basis for `WHERE` conditions or `GROUP BY` grouping when generating SQL |
| `Kibana`                   | Visualization management and debugging interface for Elasticsearch, used for index management, query debugging, and retrieval effect verification, making it convenient to observe and optimize retrieval behavior during development                                                                                 |
| `Text Embedding Inference` | Used to deploy the Embedding model inference service, converting metadata text and user questions into vector representations, providing the vector data source for `Qdrant` and serving as the foundation of semantic retrieval capability                                                                            |

From an overall division of responsibilities, they are essentially a set of mutually cooperating basic services: `MySQL` is responsible for storing structured data, `Qdrant` for semantic similarity retrieval, `Elasticsearch` for full-text matching, `Kibana` for debugging and verifying retrieval results, and the Embedding service is responsible for converting text into vectors.

> The backend code is responsible for "organizing the workflow," while these basic services are responsible for "providing data, retrieval, and vector capabilities."

### 3.5 Service Startup Method

Now that Docker is installed, configured, and started successfully, the next step is to configure the basic services required by this project. In the root directory of the `shopkeeper-agent` repository, there is a `docker` directory containing the following files:

#### 3.5.1 Prepare the Embedding Model Before Startup

There is a prerequisite step that is very easy to miss: the Embedding model needs to be downloaded separately.

The project loads `BAAI/bge-large-zh-v1.5` through `Text Embeddings Inference`. This model file is relatively large and has not been directly committed to the Git repository. In other words, the repository has the `docker/embedding/` directory convention, but before starting the basic services for the first time, you need to put the model files into it first.

The local directory required by the project is:

```text
shopkeeper-agent/docker/embedding/bge-large-zh-v1.5
```

In the root directory of the `shopkeeper-agent` project, you can use the following command to download:

```bash
uv run hf download BAAI/bge-large-zh-v1.5 --local-dir docker/embedding/bge-large-zh-v1.5
```

If you download the model manually, you should also place the extracted model files in the same directory. At minimum, you should be able to see files similar to the following in the directory:

```text
config.json
tokenizer.json
tokenizer_config.json
pytorch_model.bin
vocab.txt
```

Later, the Embedding service in `docker-compose.yaml` will read the model files here through directory mounting:

```yaml
volumes:
  - ./embedding/bge-large-zh-v1.5:/models/bge-large-zh-v1.5
```

If this directory does not exist, or if it does not contain the complete model files, the Embedding container will not be able to provide vectorization services normally even if it starts. Building the metadata knowledge base, field vector index, and metric vector index later will all depend on it, so it needs to be ready before the first `docker compose up -d`.

## 4. Analysis of the docker-compose.yaml File

### 4.1 Basic Understanding

Project file path: `shopkeeper-agent/docker/docker-compose.yaml`

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: dili123
      MYSQL_USER: didilili
      MYSQL_PASSWORD: dili123
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql
      - ./mysql:/docker-entrypoint-initdb.d
    command: --character-set-server=utf8mb4
      --collation-server=utf8mb4_general_ci

  elasticsearch:
    build: ./elasticsearch
    container_name: elasticsearch
    restart: unless-stopped
    environment:
      discovery.type: single-node
      xpack.security.enabled: "false"
    ports:
      - "9200:9200"
    volumes:
      - es_data:/usr/share/elasticsearch/data
  kibana:
    image: kibana:8.19.10
    container_name: kibana
    restart: unless-stopped
    environment:
      ELASTICSEARCH_HOSTS: http://elasticsearch:9200
    ports:
      - "5601:5601"
    depends_on:
      - elasticsearch

  qdrant:
    image: qdrant/qdrant:v1.16
    container_name: qdrant
    restart: unless-stopped
    ports:
      - "6333:6333" # HTTP
      - "6334:6334" # gRPC
    volumes:
      - qdrant_data:/qdrant/storage

  embedding:
    image: ghcr.io/huggingface/text-embeddings-inference:cpu-1.8
    platform: linux/amd64
    container_name: embedding
    restart: unless-stopped
    ports:
      - "8081:80"
    environment:
      MODEL_ID: /models/bge-large-zh-v1.5
      MAX_CONCURRENT_REQUESTS: "16"
      MAX_BATCH_TOKENS: "16384"
    volumes:
      - ./embedding/bge-large-zh-v1.5:/models/bge-large-zh-v1.5

volumes:
  mysql_data:
  es_data:
  qdrant_data:
```

If you only understand `docker compose up -d` as "a startup command," you will actually miss an important layer of engineering understanding. The `Compose` file is not simply about typing fewer commands; rather, it uses a single configuration file to clearly describe "which services this project depends on, how these services are started, how ports are mapped, how data is persisted, and how directories are mounted."

In Shopkeeper Data Q&A, this `Compose` file can be understood as: a basic service manifest. That is to say, what it describes is not a single container, but "which types of containers need to work together to make this project run."

### 4.2 Basic Services Description

- MySQL container: responsible for the metadata database and simulated data warehouse
- Elasticsearch container: responsible for full-text retrieval
- Kibana container: responsible for visualization operations on Elasticsearch
- Qdrant container: responsible for vector retrieval
- Embedding service container: responsible for converting text into vectors

Looking at these services together, you will find that what this file prepares is not five scattered containers, but three types of basic capabilities:

- **Structured data capability**: MySQL
- **Full-text retrieval capability**: Elasticsearch + Kibana
- **Vectorization and vector retrieval capability**: Embedding service + Qdrant

This is why it is important. The subsequent data Q&A workflow, metric matching, and retrieval recall are not implemented solely through business code, but are built on the premise that these types of foundational capabilities are already in place.

### 4.3 Configuration Item Details

If you follow along with this `Compose` file, the following categories of configuration are the most important to understand first:

- `image`
  Indicates directly using a pre-built image, such as `mysql:8.0`, `kibana:8.19.10`, `qdrant/qdrant:v1.16`.

- `build`
  Indicates not directly using a pre-built image, but instead building an image from the `Dockerfile` in the current directory. The `elasticsearch` here uses `build: ./elasticsearch` precisely because an additional Chinese word segmentation plugin usually needs to be installed.

- `container_name`
  Used to give the container a more intuitive name, making it easier to find later in `Docker Desktop` or on the command line.

- `restart: unless-stopped`
  Indicates that if the container stops due to an abnormal reason, it will restart automatically; it will only stop being automatically restarted if you manually stop it.

- `environment`
  Used to inject environment variables required at container startup into the container. For example:
  - MySQL is configured here with `MYSQL_ROOT_PASSWORD`, `MYSQL_USER`, `MYSQL_PASSWORD`, which are used to initialize the database password and regular user.
  - Kibana connects to Elasticsearch through `ELASTICSEARCH_HOSTS` here.
  - The Embedding service specifies the loaded model directory through `MODEL_ID` here.

- `ports`
  Used for port mapping between the host machine and the container. For example:
  - `3306:3306` means the local machine accesses MySQL through `3306`
  - `9200:9200` means the local machine accesses Elasticsearch through `9200`
  - `5601:5601` means the local machine opens Kibana through `5601`
  - `6333:6333` and `6334:6334` correspond to Qdrant's HTTP and gRPC ports respectively
  - `8081:80` means the local machine accesses the Embedding service through `8081`

- `volumes`
  Used for data persistence or directory mounting. This item is very important, because without mounting, once the container is deleted, the data or files inside it usually disappear along with it.

  Let us first distinguish between the two most common syntaxes:
  - **Named volume**
    Shaped like `mysql_data:/var/lib/mysql`. The `mysql_data` on the left is not a folder in the current directory, but rather a piece of persistent storage managed by Docker; the `/var/lib/mysql` on the right is a directory inside the container.

  - **Bind mount**
    Shaped like `./mysql:/docker-entrypoint-initdb.d`. The `./mysql` on the left is a real folder in your current project directory; the `/docker-entrypoint-initdb.d` on the right is a directory inside the container.

  The core difference between these two syntaxes can be summarized in one sentence:
  - **Named volumes** are more suitable for storing "data generated while the container is running."
  - **Bind mounts** are more suitable for making "existing files on the host machine" available to the container.

  You can also add a most direct judgment mnemonic:
  - If the left side is `./xxx`, `../xxx`, `/绝对路径/xxx`, it is usually a **bind mount**.
  - If the left side is just a name like `mysql_data`, `es_data`, `qdrant_data`, it is usually a **named volume**.

  Here is another point that is critical but also the easiest to confuse:
  - **Deleting the container** is not the same as deleting the named volume.
  - **Deleting the container** is also usually not the same as deleting the mounted directory on the host machine.

  In other words, as long as you delete only the container itself without also deleting the corresponding volume or host directory, the data usually remains. What actually tends to cause data loss is not the step of "deleting the container," but deleting the volume at the same time, or manually deleting the mounted directory on the host machine.

  In the context of the current `docker-compose.yaml`, you can understand each entry as follows:
  - `mysql_data:/var/lib/mysql`
    This is MySQL's data directory persistence. MySQL's actual data files are written to `/var/lib/mysql` inside the container, and `mysql_data` is responsible for preserving this data over the long term. This way, even if you delete the MySQL container, as long as you do not delete this volume along with it, the database data usually remains.

  - `./mysql:/docker-entrypoint-initdb.d`
    This mounts the initialization SQL scripts from the project into the MySQL container. When the official MySQL image starts for the first time, it automatically executes scripts in the `/docker-entrypoint-initdb.d` directory, so the purpose here is not to "save data," but to "hand over the database creation, table creation, and initialization data scripts to the container for execution."

  - `es_data:/usr/share/elasticsearch/data`
    This is Elasticsearch's data persistence directory. If not mounted, the index data follows the container lifecycle; once the container is deleted, the full-text search data is also easily lost.

  - `qdrant_data:/qdrant/storage`
    This is Qdrant's vector data persistence directory. It follows the same approach as MySQL and Elasticsearch: keeping the data required for retrieval in Docker's persistent storage, rather than only inside the container.

  - `./embedding/bge-large-zh-v1.5:/models/bge-large-zh-v1.5`
    This mounts the local Embedding model directory from the host machine into the container. What is mounted here is not database data, but the model files themselves. After the container starts, it reads the model weights from `/models/bge-large-zh-v1.5`.

  Additionally, this section at the bottom:

  ```yaml
  volumes:
    mysql_data:
    es_data:
    qdrant_data:
  ```

  indicates that this Compose file additionally declares 3 **named volumes**. Its meaning is: the services above use these volumes, and here they are uniformly defined.

  If we compress `volumes` into the single easiest sentence to remember, it can be understood like this:
  - The left side determines "where the data or files come from"
  - The right side determines "where the container reads from or writes to"

- `depends_on`
  Used to express dependency relationships between services. For example, `kibana` depends on `elasticsearch`. This does not mean "wait until all of Elasticsearch's business states are completely normal before starting," but rather "start the dependent service first, and then start the current service."

You can read a `Compose` file in this order:

1. Look at how many services are defined in `services`
2. Look at whether each service is `image` or `build`
3. Look at `ports` to confirm which ports the local machine uses to access them
4. Look at `volumes` to confirm which data will land on the host machine
5. Look at `environment` to confirm what configuration this service depends on at startup
6. Look at `depends_on` to confirm the dependency relationships between services

### 4.4 Detailed Analysis of Engineering Approach

Looking at each service itself, this `Compose` file also embodies several very important engineering ideas:

- **MySQL is not just starting a database container.**
  It also mounts the initialization script directory through `./mysql:/docker-entrypoint-initdb.d`. This way, when the container starts for the first time, it automatically executes the SQL files within, initializing the `meta` database, the `dw` database, the related table structures, and the mock data all at once.

- **MySQL's data directory is persisted separately.**
  The purpose of `mysql_data:/var/lib/mysql` is to mount out the directory where MySQL actually stores its data. This way, even if the container is deleted, the data will not be lost due to the disappearance of the container.

- **Elasticsearch uses `build` instead of `image`.**
  This is because the full-text search in this project is a Chinese-language scenario, which usually requires installing the additional `IK` tokenizer, so it cannot simply end by using a stock native image.

- **Kibana is essentially a debugging interface for Elasticsearch.**
  It is not a required core storage service, but it is very useful during the development stage because you can directly observe indexes, execute queries, and verify retrieval results through a web page.

- **Qdrant exposes two types of ports simultaneously.**
  One is the more commonly used HTTP port, and the other is the gRPC port. In a teaching project, it is usually sufficient to prioritize HTTP, but exposing both ports makes future expansion more convenient.

- **The Embedding service is deployed separately as an independent container.**
  This means that the "text-to-vector" process is not coupled into the business code, but is instead provided through a separate inference service, so the backend code only needs to call the service.

  It can also be supplemented with this understanding: Embedding does not have to be deployed only in this "independent service" manner. It can also be directly coupled into the business code, meaning the backend program loads the model itself and completes the text-to-vector process on its own. It is only because this tutorial series aims for a clearer engineering structure and more independent service responsibilities that it chooses the approach of "deploying it separately as an inference service."

  What runs in this container is also not the kind of "conversational large language model" we usually think of, but rather an Embedding model specifically responsible for converting text into vectors. Its job is not to generate answers, but to encode text such as field descriptions, metric descriptions, and user questions into vectors for use in subsequent vector retrieval.

- **The Embedding service mounts a local model directory.**
  The purpose of `./embedding/bge-large-zh-v1.5:/models/bge-large-zh-v1.5` is to map the local model weights into the container, and then use `MODEL_ID` to tell the service where to load the model from.

- **The teaching environment uses the CPU version of the Embedding service.**
  This is mainly to lower the barrier to local deployment. In a real production environment, if higher performance is required, the GPU version is usually used instead.

If this entire section is compressed into one easier-to-remember sentence, it can be understood like this:

> **The value of this `Compose` file is not just starting containers, but preparing the entire set of foundational capabilities—database, retrieval, and vectorization—all at once.**
