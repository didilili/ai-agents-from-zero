
The subsequent table filtering, metric filtering, and SQL generation will all continue to work around these two contexts.

## 2. Why Retrieved Results Cannot Be Passed Directly to the LLM

The information obtained from the three-route retrieval is scattered.

Field retrieval produces a list of fields, where each item is a `ColumnInfo`:

```text
retrieved_column_infos: list[ColumnInfo]
```

For example, if the user asks "calculate the total sales in North China," the field retrieval may include:

```text
fact_order.order_amount  # 订单金额字段
dim_region.region_name   # 地区名称字段
fact_order.region_id     # 订单事实表里的地区外键
```

Metric retrieval produces a list of metrics, where each item is a `MetricInfo`:

```text
retrieved_metric_infos: list[MetricInfo]
```

For example:

```text
GMV  # 销售总额、成交额
AOV  # 客单价
```

Field value retrieval produces a list of actual values, where each item is a `ValueInfo`:

```text
retrieved_value_infos: list[ValueInfo]
```

For example:

```text
dim_region.region_name.华北  # region_name 字段里的真实取值：华北
```

However, when generating SQL, the LLM would prefer to see context like this:

```text
有哪些表
每张表有哪些字段
字段类型是什么
字段角色是什么
字段有哪些示例值
指标如何定义
指标依赖哪些字段
表之间可能如何 join
```

This is like asking someone to write SQL. If you only tell them:

```text
order_amount
GMV
华北
region_name
```

They still have to guess which table each field belongs to, which fields can be joined, and which field `华北` should be used in the filter condition.

Input that is more suitable for SQL generation is a structure organized by table:

```yaml
- name: fact_order
  role: fact
  description: 订单事实表
  columns:
    - name: order_amount
      type: decimal
      role: measure
      description: 订单金额

- name: dim_region
  role: dimension
  description: 地区维度表
  columns:
    - name: region_name
      type: string
      role: dimension
      examples: ["华北"]
      description: 地区名称
```

Therefore, what `merge_retrieved_info` needs to do is not continue retrieving, but organize the scattered retrieval results into structured context.

## 3. Target Structure After Merging

![Structured process of merging retrieved information into SQL context: fields, metrics, and field values undergo deduplication, completion, and grouping to form table_infos and metric_infos](../../../%E5%AE%9E%E6%88%98%E9%A1%B9%E7%9B%AE-%E7%94%B5%E5%95%86%E9%97%AE%E6%95%B0/images/12/12-3-0-1.svg)

`merge_retrieved_info` ultimately returns two fields:

```python
return {
    "table_infos": table_infos,
    "metric_infos": metric_infos,
}
```

These two fields are written back to `DataAgentState`.

### 3.1 table_infos: Organizing Fields by Table

`table_infos` is a set of table information. Each table contains the table name, table role, table description, and the list of fields related to that table.

The approximate structure is as follows:

```python
[
    {
        "name": "fact_order",
        "role": "fact",
        "description": "订单事实表",
        "columns": [
            {
                "name": "order_amount",
                "type": "decimal",
                "role": "measure",
                "examples": [],
                "description": "订单金额",
                "alias": ["成交金额", "销售金额"],
            }
        ],
    }
]
```

The key point here is "grouping by table." Later, when generating SQL, the model not only knows that there is a field called `order_amount`, but also knows that it belongs to `fact_order`.

### 3.2 metric_infos: Organized Metric Definitions

`metric_infos` is a set of metric information. It retains what is needed for metric SQL generation:

```python
[
    {
        "name": "GMV",
        "description": "成交金额总和",
        "relevant_columns": ["fact_order.order_amount"],
        "alias": ["成交额", "交易额", "销售总额"],
    }
]
```

It is very similar to `MetricInfo` from the retrieval stage, except that the internal `id` that does not need to be shown to the model is removed.

## 4. Supplementing State and Context

### 4.1 DataAgentState: Saving the Merged Context

The merged `table_infos` and `metric_infos` will still need to be read by the filtering node and SQL generation node later, so they must be placed into `DataAgentState`.

Corresponding project file path: `shopkeeper-agent/app/agent/state.py`

```python
from typing import TypedDict

from app.entities.column_info import ColumnInfo
from app.entities.metric_info import MetricInfo
from app.entities.value_info import ValueInfo


class MetricInfoState(TypedDict):
    # 面向提示词的指标结构，不再保留内部 id
    name: str
    description: str
    relevant_columns: list[str]
    alias: list[str]


class ColumnInfoState(TypedDict):
    # 面向提示词的字段结构，只保留 SQL 生成需要理解的字段属性
    name: str
    type: str
    role: str
    examples: list
    description: str
    alias: list[str]


class TableInfoState(TypedDict):
    # 表信息会嵌套字段列表，方便后续按表组织 SQL 上下文
    name: str
    role: str
    description: str
    columns: list[ColumnInfoState]
```

Then add the merged context to `DataAgentState`:

```python
class DataAgentState(TypedDict):
    query: str  # 用户输入的查询
    keywords: list[str]  # 抽取的关键词

    retrieved_column_infos: list[ColumnInfo]  # 检索到的字段信息
    retrieved_metric_infos: list[MetricInfo]  # 检索到的指标信息
    retrieved_value_infos: list[ValueInfo]  # 检索到的取值信息

    table_infos: list[TableInfoState]  # 合并和补齐后的表结构上下文
    metric_infos: list[MetricInfoState]  # 合并后的指标上下文

    error: str  # 校验 SQL 时出现的错误信息
```

The previously defined `TableInfo`, `ColumnInfo`, and `MetricInfo` entities are not directly reused here because the merged structure has already changed.

For example, the `TableInfo` entity only describes a single table itself and does not contain `columns`; however, what the SQL generation stage needs is a nested structure of "table + fields." Therefore, `TableInfoState` is defined separately here.

Similarly, `MetricInfoState` does not need the internal `id`, and only retains the metric name, description, dependent fields, and alias.

### 4.2 DataAgentContext: Injecting Meta Repository

The merge node needs to look up complete metadata from `Meta MySQL` based on field IDs and table IDs. Therefore, `DataAgentContext` must contain `meta_mysql_repository`.

Corresponding project file path: `shopkeeper-agent/app/agent/context.py`

```python
from typing import TypedDict

from langchain_huggingface import HuggingFaceEndpointEmbeddings

from app.repositories.es.value_es_repository import ValueESRepository
from app.repositories.mysql.meta.meta_mysql_repository import MetaMySQLRepository
from app.repositories.qdrant.column_qdrant_repository import ColumnQdrantRepository
from app.repositories.qdrant.metric_qdrant_repository import MetricQdrantRepository


class DataAgentContext(TypedDict):
    # 字段向量仓储，负责根据向量从 Qdrant 检索候选字段
    column_qdrant_repository: ColumnQdrantRepository
    # Embedding 客户端，负责把关键词转换成向量检索所需的 query vector
    embedding_client: HuggingFaceEndpointEmbeddings
    # 指标向量仓储，负责根据向量从 Qdrant 检索候选指标
    metric_qdrant_repository: MetricQdrantRepository
    # 字段取值全文检索仓储，负责从 Elasticsearch 检索真实字段值
    value_es_repository: ValueESRepository
    # 元数据库仓储，合并阶段用它按 id 补齐字段、表、主外键信息
    meta_mysql_repository: MetaMySQLRepository
```

Note the division of responsibilities here:

```text
state           -> 保存本次问数链路里的业务中间结果
runtime.context -> 保存节点执行时要用的外部依赖
```

`meta_mysql_repository` is an external dependency, so it is placed in `context`, not in `state`.

## 5. Main Flow of merge_retrieved_info

First, compress the complete logic into a single flow:

```text
读取三路召回结果
  -> 把字段召回结果转成 column_id -> ColumnInfo
  -> 根据指标 relevant_columns 补齐字段
  -> 根据字段取值 column_id/value 补齐字段 examples
  -> 按 table_id 对字段分组
  -> 为每张表补充主键和外键字段
  -> 查询表信息，组装 TableInfoState
  -> 把 MetricInfo 转成 MetricInfoState
  -> 写回 table_infos 和 metric_infos
```

There are two keywords here:

- **Completion**: retrieval results may miss fields, so they need to be filled in from `Meta MySQL`;
- **Organization**: retrieval results are scattered, and ultimately need to be organized into a hierarchical structure by table.

This node does not need to call the LLM, nor does it need to access Qdrant or Elasticsearch. It only processes the information already retrieved in the previous chapter and queries `Meta MySQL` when necessary.

---

### 5.1 Node Entry: Reading state and context

Corresponding project file path: `shopkeeper-agent/app/agent/nodes/merge_retrieved_info.py`

```python
from langgraph.runtime import Runtime

from app.agent.context import DataAgentContext
from app.agent.state import (
    ColumnInfoState,
    DataAgentState,
    MetricInfoState,
    TableInfoState,
)
from app.core.log import logger
from app.entities.column_info import ColumnInfo
from app.entities.metric_info import MetricInfo
from app.entities.table_info import TableInfo
from app.entities.value_info import ValueInfo


async def merge_retrieved_info(state: DataAgentState, runtime: Runtime[DataAgentContext]):
    writer = runtime.stream_writer
    writer("合并召回信息")

    retrieved_column_infos: list[ColumnInfo] = state["retrieved_column_infos"]
    retrieved_metric_infos: list[MetricInfo] = state["retrieved_metric_infos"]
    retrieved_value_infos: list[ValueInfo] = state["retrieved_value_infos"]

    meta_mysql_repository = runtime.context["meta_mysql_repository"]
```

These lines first obtain four types of things:

- Retrieved fields: `retrieved_column_infos`
- Retrieved metrics: `retrieved_metric_infos`
- Retrieved field values: `retrieved_value_infos`
- Metadata repository: `meta_mysql_repository`

All subsequent logic revolves around these pieces of data.

---

### 5.2 Step 1: Converting the Field List into a Map

During the merge process, it is necessary to continuously determine whether a certain field already exists. If the list is traversed each time, the code becomes convoluted; therefore, the first step is to convert the field list into a Map:

```python
retrieved_column_infos_map: dict[str, ColumnInfo] = {
    retrieved_column_info.id: retrieved_column_info
    for retrieved_column_info in retrieved_column_infos
}
```

The structure of this Map is:

```text
column_id -> ColumnInfo
```

For example:

```text
fact_order.order_amount -> ColumnInfo(...)
dim_region.region_name  -> ColumnInfo(...)
```

Later, whether supplementing metric-dependent fields or supplementing the fields to which field values belong, `column_id` can be used for a quick judgment:

```python
if column_id not in retrieved_column_infos_map:
    ...
```

This step also has a natural benefit: deduplication by field ID.

---

### 5.3 Step 2: Supplementing Metric-Dependent Fields into the Field List

What metric retrieval hits is the metric, but SQL generation cannot only know the metric name.

For example, suppose `GMV` is retrieved:

```python
MetricInfo(
    id="GMV",
    name="GMV",
    description="成交金额总和",
    relevant_columns=["fact_order.order_amount"],
    alias=["成交额", "交易额", "销售总额"],
)
```

Here, `relevant_columns` records the IDs of the underlying fields that the metric depends on. In other words, if `GMV` needs to be calculated later, at least the field `fact_order.order_amount` must be known.

Therefore, the merge node must do one thing: **as long as a metric is retrieved, the fields it depends on must also enter the table field context.**

The corresponding code is as follows:

```python
# 将指标信息的相关字段信息添加到字段信息中
for retrieved_metric_info in retrieved_metric_infos:
    for relevant_column in retrieved_metric_info.relevant_columns:
        if relevant_column not in retrieved_column_infos_map:
            column_info: ColumnInfo = await meta_mysql_repository.get_column_info_by_id(
                relevant_column
            )
            retrieved_column_infos_map[relevant_column] = column_info
```

Note here that `relevant_column` is not a complete field object, but a field ID.

If this field is already in the field retrieval results, it does not need to be added again; if not, it is looked up through `Meta MySQL` and then placed into `retrieved_column_infos_map`.

In this way, when generating SQL later, the model not only knows that "the user is asking about GMV," but also knows "which underlying field should be used to calculate GMV."

---

### 5.4 Step 3: Supplementing Field Values into Field examples

What field value retrieval hits are actual values in the database, for example:

```python
ValueInfo(
    id="dim_region.region_name.华北",
    value="华北",
    column_id="dim_region.region_name",
)
```

What it means is:

```text
字段 dim_region.region_name 里存在一个真实取值：华北
```

This information is very important for SQL generation. When the user says "North China," what should actually be written in SQL may be:

```sql
where dim_region.region_name = '华北'
```

Therefore, the merge node needs to append `ValueInfo.value` to the corresponding field's `examples`.

The corresponding code is as follows:

```python
# 将字段取值加入到其所属字段的 examples 中
for retrieved_value_info in retrieved_value_infos:
    value = retrieved_value_info.value
    column_id = retrieved_value_info.column_id

    if column_id not in retrieved_column_infos_map:
        column_info: ColumnInfo = await meta_mysql_repository.get_column_info_by_id(
            column_id
        )
        retrieved_column_infos_map[column_id] = column_info

    if value not in retrieved_column_infos_map[column_id].examples:
        retrieved_column_infos_map[column_id].examples.append(value)
```

This code provides two safeguards.

First, if the field to which the field value belongs was not hit by field retrieval, the field information is first looked up from `Meta MySQL`.

This is very reasonable: since the value `华北` belongs to `dim_region.region_name`, subsequent SQL generation will most likely also need the field `dim_region.region_name`.

Second, before appending `examples`, it checks whether it already exists.

Because when building the metadata knowledge base, some fields may already have some example values attached. If `append` is used directly, the same value may appear repeatedly. Duplicate values do not help the model and can make the context messy.

By the end of this step, `retrieved_column_infos_map` already contains three types of fields:

- Fields directly hit by field retrieval;
- Fields supplemented from metric dependencies;
- Fields supplemented from the fields to which field values belong.

---

### 5.5 Step 4: Grouping Fields by Table

What has been maintained so far is still a field Map:

```text
column_id -> ColumnInfo
```

But what ultimately needs to be provided to the LLM is a structure organized by table. Therefore, the next step is to group by `table_id`.

The code is as follows:

```python
# 按照表对字段信息进行分组
table_to_columns_map: dict[str, list[ColumnInfo]] = {}

for column_info in retrieved_column_infos_map.values():
    table_id = column_info.table_id
    if table_id not in table_to_columns_map:
        table_to_columns_map[table_id] = []
    table_to_columns_map[table_id].append(column_info)
```

The structure obtained in this step is:

```text
table_id -> list[ColumnInfo]
```

For example:

```text
fact_order -> [
  fact_order.order_amount,
  fact_order.region_id
]

dim_region -> [
  dim_region.region_name
]
```

There is a small detail here: before appending a field each time, it is necessary to check whether `table_id` is already in the Map.

If a table is encountered for the first time, an empty list is initialized first:

```python
table_to_columns_map[table_id] = []
```

Otherwise, calling `append` directly will raise an error because the key cannot be found.

---

### 5.6 Step 5: Supplementing Primary Keys and Foreign Keys for Each Table

This section is the most easily overlooked but very important step in this chapter.

When retrieving fields by vector, primary keys and foreign keys are not always hit reliably. The reason is simple: primary and foreign key fields often have weak semantic meaning.

For example, the primary key of many tables is called:

```text
id
```

Or the foreign key is called:

```text
region_id
customer_id
product_id
```

These fields are very important for SQL `join`, but they do not necessarily appear in natural language questions. When the user asks:

```text
统计华北地区的销售总额
```

Retrieval may hit `region_name` and `order_amount`, but may not necessarily hit:

```text
dim_region.region_id
fact_order.region_id
```

If these primary and foreign keys are missing from the subsequent context, it will be difficult for the model to write the correct join conditions:

```sql
fact_order.region_id = dim_region.region_id
```

Therefore, after "grouping by table," the merge node explicitly supplements the primary key and foreign key fields of each table.

Why is the enrichment done after grouping?

Because only after grouping do we know which tables are currently involved. Once we know the table IDs, we can query all `primary_key` and `foreign_key` fields under that table.

The corresponding code is as follows:

```python
# 强制为每个表添加主外键字段
for table_id in table_to_columns_map.keys():
    key_columns: list[ColumnInfo] = await meta_mysql_repository.get_key_columns_by_table_id(
        table_id
    )
    column_ids = [column_info.id for column_info in table_to_columns_map[table_id]]

    for key_column in key_columns:
        if key_column.id not in column_ids:
            table_to_columns_map[table_id].append(key_column)
```

You cannot directly use the following here:

```python
if key_column not in table_to_columns_map[table_id]:
    ...
```

Because `key_column` is an object. When comparing objects directly, it is very easy to end up comparing object addresses rather than comparing field IDs. A more reliable approach here is to first get the field IDs that already exist in the current table:

```python
column_ids = [column_info.id for column_info in table_to_columns_map[table_id]]
```

Then judge whether it already exists based on `key_column.id`.

Adding primary and foreign keys brings a side effect: it may bring in some fields that are temporarily not needed for the current question. This problem is acceptable, because the filtering node in the next chapter will continue to streamline the context. Here, the priority is to ensure that the SQL generation does not lack the fields required for joins.

---

### 5.7 Step 6: Assembling TableInfoState

Now we already have:

```text
table_id -> list[ColumnInfo]
```

But the final `state["table_infos"]` requires:

```text
list[TableInfoState]
```

So another conversion is needed.

The code is as follows:

```python
# 将表信息整理成目标格式
table_infos: list[TableInfoState] = []

for table_id, column_infos in table_to_columns_map.items():
    table_info: TableInfo = await meta_mysql_repository.get_table_info_by_id(table_id)

    columns = [
        ColumnInfoState(
            name=column_info.name,
            type=column_info.type,
            role=column_info.role,
            examples=column_info.examples,
            description=column_info.description,
            alias=column_info.alias,
        )
        for column_info in column_infos
    ]

    table_info_state = TableInfoState(
        name=table_info.name,
        role=table_info.role,
        description=table_info.description,
        columns=columns,
    )
    table_infos.append(table_info_state)
```

This step performs two layers of conversion.

In the first layer, `ColumnInfo` is converted into `ColumnInfoState`.

`ColumnInfo` contains internal fields such as `id` and `table_id`, but not all of them are necessarily needed in the prompt context. What is retained here are the fields more suitable for the large language model to read:

```text
name
type
role
examples
description
alias
```

In the second layer, the table information and the field list are combined into `TableInfoState`.

What `get_table_info_by_id(table_id)` retrieves are the table name, table role, and table description; `columns` comes from the field list after the previous grouping. Only when the two are combined do they form the table structure context needed for subsequent SQL generation.

---

### 5.8 Step 7: Assembling MetricInfoState

Compared with table information, the processing of metric information is much simpler.

What retrieval obtains is `MetricInfo`:

```python
MetricInfo(
    id="GMV",
    name="GMV",
    description="成交金额总和",
    relevant_columns=["fact_order.order_amount"],
    alias=["成交额", "交易额", "销售总额"],
)
```

What ultimately needs to be written into `state` is `MetricInfoState`:

```python
class MetricInfoState(TypedDict):
    name: str
    description: str
    relevant_columns: list[str]
    alias: list[str]
```

The main difference is that the internal `id` is removed. The code can be completed with a list comprehension:

```python
# 处理指标信息
metric_infos: list[MetricInfoState] = [
    MetricInfoState(
        name=retrieved_metric_info.name,
        description=retrieved_metric_info.description,
        relevant_columns=retrieved_metric_info.relevant_columns,
        alias=retrieved_metric_info.alias,
    )
    for retrieved_metric_info in retrieved_metric_infos
]

return {
    "table_infos": table_infos,
    "metric_infos": metric_infos,
}
```

At this point, the core logic of the `merge_retrieved_info` node is complete.

## 6. Complete Node Code

Combining the above steps, the complete node is as follows.

Corresponding file path in the project: `shopkeeper-agent/app/agent/nodes/merge_retrieved_info.py`

```python
from langgraph.runtime import Runtime

from app.agent.context import DataAgentContext
from app.agent.state import (
    ColumnInfoState,
    DataAgentState,
    MetricInfoState,
    TableInfoState,
)
from app.core.log import logger
from app.entities.column_info import ColumnInfo
from app.entities.metric_info import MetricInfo
from app.entities.table_info import TableInfo
from app.entities.value_info import ValueInfo


async def merge_retrieved_info(
    state: DataAgentState, runtime: Runtime[DataAgentContext]
):
    """合并召回结果，并输出 SQL 生成前的候选表信息和指标信息"""

    writer = runtime.stream_writer
    writer("合并召回信息")

    retrieved_column_infos: list[ColumnInfo] = state["retrieved_column_infos"]
    retrieved_metric_infos: list[MetricInfo] = state["retrieved_metric_infos"]
    retrieved_value_infos: list[ValueInfo] = state["retrieved_value_infos"]

    meta_mysql_repository = runtime.context["meta_mysql_repository"]

    # 本节点的主线是：
    # 字段召回 + 指标依赖字段 + 字段真实取值 + 主外键补齐
    # -> table_infos / metric_infos，交给后续过滤和 SQL 生成节点继续使用。

    # 1. 以 column_id 为 key 合并字段信息
    # 三路召回可能命中同一个字段，用 dict 可以自然去重；
    # 后续指标依赖字段和字段取值也都通过 column_id 合并进来。
    retrieved_column_infos_map: dict[str, ColumnInfo] = {
        retrieved_column_info.id: retrieved_column_info
        for retrieved_column_info in retrieved_column_infos
    }

    # 2. 补齐指标依赖字段
    # 指标告诉模型“怎么算”，但生成 SQL 还需要知道指标依赖哪些真实字段。
    # 如果相关字段没有被字段召回命中，就从 Meta MySQL 里按 id 查出来补进上下文。
    for retrieved_metric_info in retrieved_metric_infos:
        for relevant_column in retrieved_metric_info.relevant_columns:
            if relevant_column not in retrieved_column_infos_map:
                column_info: ColumnInfo = (
                    await meta_mysql_repository.get_column_info_by_id(relevant_column)
                )
                retrieved_column_infos_map[relevant_column] = column_info

    # 3. 把字段取值合并回字段 examples
    # 字段取值召回命中的是 column_id + value，例如 dim_region.region_name.华北。
    # 把真实 value 放进字段 examples，可以帮助模型写出更接近真实数据的 where 条件。
    for retrieved_value_info in retrieved_value_infos:
        value = retrieved_value_info.value
        column_id = retrieved_value_info.column_id
        if column_id not in retrieved_column_infos_map:
            column_info: ColumnInfo = await meta_mysql_repository.get_column_info_by_id(
                column_id
            )
            retrieved_column_infos_map[column_id] = column_info
        if value not in retrieved_column_infos_map[column_id].examples:
            retrieved_column_infos_map[column_id].examples.append(value)

    # 4. 按表组织字段上下文
    # SQL 生成提示词通常按“表 -> 字段列表”的方式描述结构，
    # 所以这里先把分散的字段按 table_id 归到各自所属表下面。
    table_to_columns_map: dict[str, list[ColumnInfo]] = {}
    for column_info in retrieved_column_infos_map.values():
        table_id = column_info.table_id
        if table_id not in table_to_columns_map:
            table_to_columns_map[table_id] = []
        table_to_columns_map[table_id].append(column_info)

    # 5. 补齐主外键字段
    # 主外键通常不会出现在用户问题里，单靠向量召回容易漏掉；
    # 但多表查询的 Join 路径必须依赖它们，所以每张候选表都要兜底补齐。
    for table_id in table_to_columns_map.keys():
        key_columns: list[
            ColumnInfo
        ] = await meta_mysql_repository.get_key_columns_by_table_id(table_id)
        column_ids = [column_info.id for column_info in table_to_columns_map[table_id]]
        for key_column in key_columns:
            if key_column.id not in column_ids:
                table_to_columns_map[table_id].append(key_column)

    # 6. 生成表结构上下文
    # 数据库实体里可能包含入库和索引用字段，传给模型前只保留必要信息，
    # 让后续过滤和 SQL 生成节点面对的是更稳定的 TableInfoState 结构。
    table_infos: list[TableInfoState] = []
    for table_id, column_infos in table_to_columns_map.items():
        table_info: TableInfo = await meta_mysql_repository.get_table_info_by_id(
            table_id
        )
        columns = [
            ColumnInfoState(
                name=column_info.name,
                type=column_info.type,
                role=column_info.role,
                examples=column_info.examples,
                description=column_info.description,
                alias=column_info.alias,
            )
            for column_info in column_infos
        ]
        table_info_state = TableInfoState(
            name=table_info.name,
            role=table_info.role,
            description=table_info.description,
            columns=columns,
        )
        table_infos.append(table_info_state)

    # 7. 生成指标上下文
    # 指标上下文保留名称 描述 别名和依赖字段，足够让模型理解业务口径。
    metric_infos: list[MetricInfoState] = [
        MetricInfoState(
            name=retrieved_metric_info.name,
            description=retrieved_metric_info.description,
            relevant_columns=retrieved_metric_info.relevant_columns,
            alias=retrieved_metric_info.alias,
        )
        for retrieved_metric_info in retrieved_metric_infos
    ]

    logger.info(f"合并后的表信息：{[table_info['name'] for table_info in table_infos]}")
    logger.info(
        f"合并后的指标信息：{[metric_info['name'] for metric_info in metric_infos]}"
    )

    return {"table_infos": table_infos, "metric_infos": metric_infos}
```

Although this code looks long, there are only two mainlines:

```text
表信息：字段 Map -> 补指标字段 -> 补字段值 -> 按表分组 -> 补主外键 -> TableInfoState
指标信息：MetricInfo -> MetricInfoState
```

## 7. Methods to Add to MetaMySQLRepository

The merging node needs to query three types of information from `Meta MySQL`:

- Query complete field information by field ID;
- Query complete table information by table ID;
- Query the primary key and foreign key fields of this table by table ID.

Therefore, three methods need to be added to `MetaMySQLRepository`.

Corresponding file path in the project: `shopkeeper-agent/app/repositories/mysql/meta/meta_mysql_repository.py`

### 7.1 Query Fields by Field ID

```python
async def get_column_info_by_id(self, id: str) -> ColumnInfo | None:
    """按字段 id 查询字段元数据，供召回信息合并阶段补齐字段上下文"""
    column_info: ColumnInfoMySQL | None = await self.session.get(ColumnInfoMySQL, id)
    if column_info:
        # Repository 对外返回业务实体，不把 ORM Model 泄露给 Agent 节点
        return ColumnInfoMapper.to_entity(column_info)
    else:
        return None
```

What is used here is SQLAlchemy's `session.get(...)`. It is suitable for querying a single record by primary key.

What is retrieved is an ORM Model: `ColumnInfoMySQL`. The business layer prefers to use the entity object `ColumnInfo`, so a conversion is performed at the end through `ColumnInfoMapper.to_entity(...)`.

### 7.2 Query Tables by Table ID

```python
async def get_table_info_by_id(self, id: str) -> TableInfo | None:
    """按表 id 查询表元数据，最终组装成提示词里的表结构信息"""
    table_info: TableInfoMySQL | None = await self.session.get(TableInfoMySQL, id)
    if table_info:
        return TableInfoMapper.to_entity(table_info)
    else:
        return None
```

This logic is similar to querying fields, except that the query target is changed to `TableInfoMySQL`.

During the merging stage, it is used to supplement the table name, table role, and table description.

### 7.3 Query Primary and Foreign Key Fields by Table ID

```python
from sqlalchemy import select


async def get_key_columns_by_table_id(self, table_id: str) -> list[ColumnInfo]:
    """查询指定表的主外键字段，避免 Join 关键字段被向量召回漏掉"""
    # 主外键字段用于后续生成 join 条件，不能完全依赖向量召回命中
    # 使用 ORM 列类型信息，让 examples / alias 两个 JSON 列正确解析为列表
    stmt = select(ColumnInfoMySQL).where(
        ColumnInfoMySQL.table_id == table_id,
        ColumnInfoMySQL.role.in_(("primary_key", "foreign_key")),
    )
    result = await self.session.scalars(stmt)
    return [ColumnInfoMapper.to_entity(model) for model in result.all()]
```

This query performs two layers of filtering: it only queries the specified table, and it only retains primary key or foreign key fields. It has the same meaning as the following SQL condition:

```sql
where table_id = :table_id
  and role in ('primary_key','foreign_key')
```

Here, `table_id` is bound as a query parameter through a SQLAlchemy expression, so it does not need to be concatenated into the SQL string.

More importantly, the type of the return value: `ColumnInfoMySQL` declares `examples` and `alias` as JSON columns. When using `select(ColumnInfoMySQL)` for the query, SQLAlchemy parses the database results according to these column types, `session.scalars(...)` obtains the ORM model, and then `ColumnInfoMapper.to_entity(...)` uniformly converts it into a business entity, consistent with `get_column_info_by_id()`.

**Chapter Summary:**

This chapter implemented the `merge_retrieved_info` node in the data query agent.

The entire chapter can be compressed into the following chain:

```text
retrieved_column_infos
retrieved_metric_infos
retrieved_value_infos
  -> 字段按 id 转 Map
  -> 指标依赖字段补进字段 Map

  -> 字段按 table_id 分组
  -> 每张表补主键和外键
  -> 组装 table_infos
  -> 组装 metric_infos
```

At this point, the fields, metrics, and values that were previously retrieved in a scattered manner have been organized into a structured context that is easier for the large language model to understand. What the next chapter needs to do is continue filtering based on this context, further compressing the tables, fields, and metrics that are not closely related to the current question.
